# PHP SDK

## Requirements

- PHP 8.2+ with the `curl`, `json` and `openssl` extensions (CI uses 8.3)
- Composer
- JDK 17+ to run the Gradle code generation (CI uses 21)

The SDK has no runtime dependencies beyond these extensions; PHPUnit is a development dependency.

## Wirespec version

The PHP client is generated by Wirespec's PHP emitter, which is not in a Wirespec release yet. Until it is, publish
Wirespec from source to Maven Local once; the PHP package resolves version `0.0.0-SNAPSHOT` from there (`wirespecPhp`
in `gradle/libs.versions.toml`). Run this next to the bunq-sdk checkout:

```bash
git clone https://github.com/flock-community/wirespec.git
cd wirespec
./gradlew \
  :src:compiler:core:publishJvmPublicationToMavenLocal :src:compiler:core:publishKotlinMultiplatformPublicationToMavenLocal \
  :src:compiler:emitters:php:publishJvmPublicationToMavenLocal :src:compiler:emitters:php:publishKotlinMultiplatformPublicationToMavenLocal \
  :src:converter:common:publishJvmPublicationToMavenLocal :src:converter:common:publishKotlinMultiplatformPublicationToMavenLocal \
  :src:converter:openapi:publishJvmPublicationToMavenLocal :src:converter:openapi:publishKotlinMultiplatformPublicationToMavenLocal
```

The other packages use the Wirespec Gradle plugin 0.22.4, which buildSrc puts on the build classpath. The PHP package
therefore does not apply the plugin: `:packages:php:wirespec` runs a small generator (`packages/php/codegen`) in its own
JVM with the snapshot compiler. Once a Wirespec release has the PHP emitter, the package can switch to the plugin with
`languages = listOf(Language.Php)`.

## Setup

The package is not published to Packagist, and the generated code in `packages/php/gen` is not committed. Generate it
and install the dependencies (run this from the repository root):

```bash
./gradlew :packages:php:wirespec
cd packages/php
composer install
```

The generated code lives in the `Bunq\Api` namespace (`Bunq\Api\Model`, `Bunq\Api\Endpoint`, `Bunq\Api\Client`, ...),
the hand-written SDK in `Bunq\Sdk`. An endpoint file declares several classes (`ReadUser`, `ReadUser\Request`,
`ReadUser\Response200`, ...), so Composer loads `gen/` with a classmap: run `composer dump-autoload` after generating
the code again.

## Creating a Context

```php
use Bunq\Sdk\Bunq;
use Bunq\Sdk\BunqServer;
use Bunq\Sdk\Config;
use Bunq\Sdk\SigningKeys;

$config = new Config(
    bunqServer: BunqServer::sandbox(),
    serviceName: 'MyApp',
    apiKey: 'your-api-key',
    signingKeys: SigningKeys::fromFiles('private_key.pem', 'public_key.pem'),
);
$context = Bunq::initContext($config);
```

`SigningKeys::fromFiles` reads the key pair from the two files, or generates one and writes it there the first time.
`SigningKeys::generate()` creates a new pair on every call, and `Config::create(...)` takes the keys as PEM strings: a
PKCS#8 private key (`-----BEGIN PRIVATE KEY-----`) and its X.509 public key (`-----BEGIN PUBLIC KEY-----`). A key that
cannot be used throws `SigningKeyValidationError`, which says what is wrong and how to fix it, for example how to
convert a PKCS#1 key.

## Creating the Client and Calling an Endpoint

`Bunq::client($context)` returns the client that Wirespec generates, `Bunq\Api\Client`, with one method per bunq
operation, named after the operation id in camelCase (`readUser`, `listAllMonetaryAccountBankForUser`). Pass `null`
for query parameters you do not use. Check the response class (`Response200` or `Response400`) to read the typed body;
any other status throws `BunqApiError` (see Error Handling).

```php
use Bunq\Api\Endpoint\ListAllMonetaryAccountBankForUser;
use Bunq\Api\Endpoint\ReadUser;

$client = Bunq::client($context);

$user = $client->readUser($context->userId);
if ($user instanceof ReadUser\Response200) {
    echo $user->body->UserPerson?->legal_name, PHP_EOL;
} else {
    throw new RuntimeException('Received 400: ' . $user->body->Error[0]->error_description);
}

$accounts = $client->listAllMonetaryAccountBankForUser($context->userId, count: null, newer_id: null, older_id: null);
if ($accounts instanceof ListAllMonetaryAccountBankForUser\Response200) {
    foreach ($accounts->body->Response as $account) {
        echo $account->display_name, PHP_EOL;
    }
}
```

Every model has `validate()`, which returns the paths of the values that break a constraint of the specification.

## Pagination

A list operation returns a page, `<Item>Page` (for example `PaymentPage`), with the items in `Response` and bunq's
`Pagination` block in `Pagination`. `Pagination` has `future_url`, `newer_url` and `older_url`; each is null when there
is nothing to follow. Items are listed newest first. To read the next (older) page, call the operation again with
`older_id` set to the id of the last item of the current page. `count` is the page size (at most 200).

```php
use Bunq\Api\Endpoint\ListAllPaymentForUserMonetaryAccount;

function allPayments(Bunq\Api\Client $client, int $userId, int $monetaryAccountId): array
{
    $payments = [];
    $olderId = null;
    do {
        $response = $client->listAllPaymentForUserMonetaryAccount($userId, $monetaryAccountId, count: 200, newer_id: null, older_id: $olderId);
        if (!$response instanceof ListAllPaymentForUserMonetaryAccount\Response200) {
            throw new RuntimeException('Cannot list payments');
        }
        $page = $response->body;
        $payments = [...$payments, ...$page->Response];
        $olderId = $page->Response === [] ? null : $page->Response[\array_key_last($page->Response)]->id;
    } while ($page->Pagination->older_url !== null && $page->Response !== []);
    return $payments;
}
```

## Session Refresh

See [Session Refresh in the README](../README.md#session-refresh) for how the client refreshes the session, and what
happens when the refresh fails (the call throws `BunqApiError` with status 403). PHP runs one request at a time, so
there is no shared refresh between concurrent calls; the refresh-failure warning is written with `error_log`.

`Bunq::refreshSession($context)` creates a new session with the same device and installation and returns a new
`Context`. An existing client does not pick it up; create a new client from the returned context.

## Persist and restore a Context

`Bunq::initContext` registers an installation and a device, which you only need once per API key. Store the `Context`
and build the client from it on the next request instead of calling `initContext` again: every field of `Context`
(`serverPublicKey`, `deviceId`, `sessionId`, `sessionToken`, `userId`, `sessionExpiryTime`, `installationToken`) and
the secrets in `config`. Treat the stored data as a secret and store it encrypted.

Pass a callback to `Bunq::client` to receive the new `Context` after every refresh, whether triggered by a 403 or by
expiry:

```php
$client = Bunq::client($restored, onContextChange: static function (Bunq\Sdk\Context $context): void {
    save($context);
});
```

If `sessionExpiryTime` is in the past or less than 30 seconds away, the client refreshes the session before the first
request, so a stored context that expired in the meantime works. If bunq no longer accepts the stored installation or
device, the refresh fails; call `Bunq::initContext` again.

`var_dump` and `print_r` of `Context` and `Config` mask the tokens, the API key and the private key; the object still
holds them.

## Response Signatures

bunq signs every response: the `X-Bunq-Server-Signature` header holds a base64 SHA256withRSA (PKCS#1 v1.5) signature
over the raw response body bytes. Every 200 and 400 response that reaches the generated client is verified against
`$context->serverPublicKey`; a response without a valid signature throws
`UnexpectedValueException('Invalid bunq server signature')`. The installation response itself is not verified: the
key it carries is not known yet.

## Error Handling

See [Error Handling in the README](../README.md#error-handling) for when the error is thrown.

A 400 is returned as `Response400`, whose body has `Error` (a list with an `error_description` per entry). Every other
outcome throws `Bunq\Sdk\BunqApiError`, which has `status` and `body`, the full response body as a string; the message
is `Received <status>: <first 500 characters>`:

```php
use Bunq\Sdk\BunqApiError;

try {
    $user = $client->readUser($userId);
} catch (BunqApiError $e) {
    if ($e->status !== 404) {
        throw $e;
    }
}
```

`Bunq::initContext` and `Bunq::refreshSession` throw a `RuntimeException` if a step fails with a typed 400, with a
message like `Session server creation failed (status 400): <error_description>` (the steps are "Installation failed",
"Device server creation failed" and "Session server creation failed"); any other status throws `BunqApiError`.

## Tests

```bash
cd packages/php
composer test                                # all tests, including the sandbox tests
vendor/bin/phpunit --exclude-group sandbox   # without network access
```

The sandbox tests create a fresh sandbox user and call the bunq sandbox.
